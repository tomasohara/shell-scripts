  There are three distinct LINENO behaviors happening in that trace, all caused by running trace-cmd (defined in  
  tomohara-aliases.bash:2873-2895) directly from an interactive shell:                                            
                                                                                                                  
  ### 1. Function-relative line numbers (3, 6, 7, 10… in is-true and 10, 11, 12… in trace-cmd)                    
                                                                                                                  
  When tomohara-aliases.bash is sourced, Bash records the true file line numbers on the parsed AST nodes for      
  is-true and trace-cmd, along with each function's starting line (function_line_number).                         
                                                                                                                  
  However, when a function is executed, Bash's internal command runners (execute_simple_command,                  
  execute_cond_command, etc. in execute_cmd.c) check whether the call originated from an interactive prompt       
  (interactive_shell != 0 and sourcelevel == 0):                                                                  
                                                                                                                  
    if (variable_context && interactive_shell && sourcelevel == 0)                                                
      {
        line_number -= function_line_number;
        if (line_number < 0)
          line_number = 0;
      }
  
  Even though ${BASH_SOURCE} still resolves to tomohara-aliases.bash, sourcelevel is 0 at the interactive prompt  
  (and interactive_shell remains 1 inside the ( ... ) subshell of trace-cmd), so Bash subtracts the function's    
  starting line number from LINENO, making LINENO relative to the function definition.
  
  ### 2. Why case "$value" in jumps back to :636: (absolute file line number)
  
  In Bash (through 5.2), execute_simple_command and execute_cond_command ([[ ... ]]) apply the line_number -=     
  function_line_number adjustment above, but execute_case_command does not. It sets line_number = case_command-   
  >line directly before printing the xtrace line for case "$value" in, exposing the unadjusted file line number   
  (636 in your file) for that single line before the inner assignment (result=false) drops back to function-      
  relative line 16.
  
  ### 3. Why $(...) and eval reset LINENO to :1:
  
  Every line showing :1: occurs inside either a command substitution $(...) or eval:
  
  • $(is-true "EVAL_COMMAND") → :1: is-true EVAL_COMMAND
  • $(eval echo "\${$env_name:-false}") → :1: eval ... and :1: echo false
  • $(echo "$value" | tr ...) → :1: echo false and :1: tr ...
  • $(alias "$1" 2> /dev/null) → :1: alias pwd-host-info
  • eval "$*" → :1: pwd, :1: echo vivo, :1: uname -n
  
  When interactive_shell && sourcelevel == 0, Bash's parse_and_execute() treats the string inside $(...) or eval  
  as a fresh interactive command buffer starting at line 1 instead of preserving the surrounding script line      
  number.
  ──────
  ### Workaround (if you want absolute file line numbers)
  
  Because Bash only subtracts function_line_number (and resets eval/$(...) to 1) when sourcelevel == 0, invoking  
  the command via source (which increments sourcelevel to 1) preserves the exact file line numbers from           
  tomohara-aliases.bash:
  
    PS4='+ ${BASH_SOURCE}:${LINENO}: ' source <(echo "trace-cmd pwd-host-info") | cat
  
  (Or inside trace-cmd, running the traced body while sourcelevel > 0 or in a non-interactive shell will report   
  the file line numbers 2882, 627, 630, 631, etc.)
